# 客户端和服务端自动升级功能方案

## 1. 结论

本项目的客户端和服务端都是 Tauri 2 + Vue 应用，并通过 NSIS 生成 Windows 安装包。

自动升级功能建议采用“程序内检测 + Tauri Updater 下载安装 + NSIS 安装脚本配合”的方式实现。

也就是说：

- 程序里负责启动时检测新版本、弹出确认框、下载更新包、触发安装和重启。
- NSIS 负责安装阶段停止旧进程、覆盖旧文件、写入卸载信息、创建快捷方式等。
- 服务端的 Go 后端程序 `backend-server.exe` 不需要单独做升级逻辑，因为它已经作为 Tauri 服务端程序的资源一起打包，升级服务端安装包时会一起被替换。

## 2. 为什么不能只放在 NSIS 里做

NSIS 安装脚本只有在安装包运行时才会执行。用户日常打开软件时，NSIS 不会自动运行，所以它不能负责“打开软件时自动检测有没有新版本”。

打开软件时检测更新，必须放在客户端和服务端程序运行时逻辑里。

NSIS 需要配合的地方主要是：

- 安装新版本前停止旧版本进程。
- 服务端升级时停止 `backend-server.exe`。
- 覆盖安装目录里的旧程序文件。
- 不要误删用户数据、数据库和配置。

## 3. 当前项目情况

客户端：

- 项目目录：`boer-lan-client`
- 当前版本：`1.0.23`
- 安装包目标：NSIS
- 配置文件：`boer-lan-client/src-tauri/tauri.conf.json`

服务端：

- 项目目录：`boer-lan-server`
- 当前版本：`1.0.23`
- 安装包目标：NSIS
- 配置文件：`boer-lan-server/src-tauri/tauri.conf.json`
- 服务端程序会携带资源：
  - `backend-server*`
  - `config/*`

服务端数据目录需要特别注意：

- Windows 默认数据目录：`%APPDATA%\com.boer.lan-server`
- 数据库文件：`%APPDATA%\com.boer.lan-server\boer-lan.db`
- 端口文件：`%APPDATA%\com.boer.lan-server\backend-port.txt`

## 4. 推荐技术方案

使用 Tauri 官方 updater 插件。

需要分别给客户端和服务端配置更新地址。

建议地址分开：

```text
https://你的域名/update/client/latest.json
https://你的域名/update/server/latest.json
```

也可以用同一个域名下不同路径区分：

```text
https://你的域名/boer-lan/client/latest.json
https://你的域名/boer-lan/server/latest.json
```

## 5. 更新检测流程

软件启动后执行：

1. 读取当前程序版本。
2. 请求更新检测地址。
3. 如果没有新版本，静默继续进入系统。
4. 如果有新版本，弹出确认框：

```text
发现新版本 V1.0.24

是否下载并安装新版本？

[下载并安装] [取消]
```

5. 用户点击“取消”：
   - 本次不更新。
   - 正常进入系统。

6. 用户点击“下载并安装”：
   - 下载新版本安装包。
   - 显示下载进度。
   - 下载完成后触发安装。
   - 安装完成后重启软件。

## 6. 更新接口格式

当没有新版本时，推荐返回：

```http
204 No Content
```

当有新版本时，返回 JSON：

```json
{
  "version": "1.0.24",
  "notes": "修复已知问题，优化自动升级功能。",
  "pub_date": "2026-05-17T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://你的域名/update/client/Boer-LAN-Manager_1.0.24_x64-setup.exe",
      "signature": "这里填写安装包签名内容"
    }
  }
}
```

服务端示例：

```json
{
  "version": "1.0.24",
  "notes": "修复服务端问题，更新后台服务程序。",
  "pub_date": "2026-05-17T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://你的域名/update/server/Boer-LAN-Server_1.0.24_x64-setup.exe",
      "signature": "这里填写安装包签名内容"
    }
  }
}
```

## 7. 版本号规则

版本号必须递增，否则不会触发更新。

例如：

```text
1.0.23 -> 1.0.24
1.0.24 -> 1.0.25
1.0.25 -> 1.1.0
```

每次发布新版本时，需要同步修改：

客户端：

- `boer-lan-client/package.json`
- `boer-lan-client/src-tauri/tauri.conf.json`
- `boer-lan-client/src-tauri/Cargo.toml`

服务端：

- `boer-lan-server/package.json`
- `boer-lan-server/src-tauri/tauri.conf.json`
- `boer-lan-server/src-tauri/Cargo.toml`

如果窗口标题里也显示版本号，也要同步修改标题。

## 8. 客户端需要改动

客户端需要增加：

- Tauri updater Rust 插件依赖。
- Tauri updater 前端 JS 依赖。
- `tauri.conf.json` 中的 updater 配置。
- 启动后自动检测更新的前端逻辑。
- 弹出“下载新版本 / 取消”的确认框。
- 下载进度提示。
- 下载完成后自动安装并重启。

建议检测时机：

- 试用状态检测通过之后。
- Vue 应用正常挂载之后。
- 避免在试用错误、网络错误页面上重复弹框。

## 9. 服务端需要改动

服务端同样需要增加：

- Tauri updater Rust 插件依赖。
- Tauri updater 前端 JS 依赖。
- `tauri.conf.json` 中的 updater 配置。
- 启动后自动检测更新的前端逻辑。
- 弹出“下载新版本 / 取消”的确认框。
- 下载进度提示。
- 下载完成后自动安装并重启。

服务端额外注意：

- 安装新版本前需要停止主程序。
- 安装新版本前需要停止 `backend-server.exe`。
- 新安装包里要携带最新的 `backend-server.exe`。
- 升级时不能删除数据库和用户配置。

## 10. NSIS 需要调整的地方

当前 NSIS hook 会在安装前停止进程，这是需要保留的。

客户端目前会停止：

```text
${MAINBINARYNAME}.exe
```

服务端目前会停止：

```text
${MAINBINARYNAME}.exe
backend-server.exe
```

这是合理的。

但是当前 NSIS hook 还会清理本地数据目录，这对自动升级有风险。

需要重点检查并修改这些逻辑：

```nsh
RMDir /r "$APPDATA\${BUNDLEID}"
RMDir /r "$LOCALAPPDATA\${BUNDLEID}"
RMDir /r "$APPDATA\BoerLAN"
RMDir /r "$LOCALAPPDATA\BoerLAN"
```

自动升级时不能删除这些目录，尤其是服务端：

```text
%APPDATA%\com.boer.lan-server
```

因为服务端数据库就在这个目录下。

建议调整为：

- 升级安装只删除安装目录里的程序文件。
- 不删除 `%APPDATA%` 和 `%LOCALAPPDATA%` 下的数据。
- 如果确实需要清理数据，应该单独做“卸载并清除数据”的选项，而不是每次安装都清理。

## 11. 发布流程

每次发布新版本时，按下面流程执行：

1. 修改客户端和服务端版本号。
2. 构建客户端安装包。
3. 构建服务端安装包。
4. 生成 updater 签名文件。
5. 上传安装包到服务器。
6. 上传或更新 `latest.json`。
7. 老版本启动后检测到新版本。
8. 用户确认后自动下载安装。

## 14. 风险点

自动升级前必须处理以下风险：

- 服务端数据库不能被 NSIS hook 删除。
- 服务端升级时必须停止 `backend-server.exe`，否则可能覆盖失败。
- 更新地址必须稳定可访问。
- 每个安装包必须有正确签名。
- 客户端和服务端最好使用不同更新地址，避免客户端下载服务端安装包。
- 版本号必须严格递增。

## 15. 后续实施顺序

建议按这个顺序做：

1. 先确认最终更新检测地址。
2. 修改客户端 updater 配置和启动检测逻辑。
3. 修改服务端 updater 配置和启动检测逻辑。
4. 调整 NSIS hook，避免升级时删除数据。
5. 打一个 `1.0.24` 测试包。
6. 部署 `latest.json` 和安装包到服务器。
7. 用旧版本 `1.0.23` 测试自动检测、下载、安装、重启。
8. 确认服务端数据库、配置、端口文件都保留。
